# SmartChart chart-selection law v2.0 — research before rendering

Updated 2026-11-01. **All 40 chart styles must be evaluated against the dataset and intended question before selecting or rendering any visual.** This document is an editorial procedure; the executable implementation is `src/engine.mjs → evaluateChartCandidates()`, and the complete historically grounded examples and caveats live in `atlas/catalog.json`.

## Decision protocol (mandatory for every new chart)

1. **Read the data, then define the claim.** Specify each variable's analytical role (time, categorical, numeric, grouping, geographic, range, before/after, total, component, probability) and whether it represents observed, modeled, contracted, planned, or speculative data. Give units, dates, normalization, and full primary source citations.
2. **Audit the complete 40-chart atlas** programmatically or by its reference matrix below; do not restrict the candidate set to the 8–9 currently available renderers. For every style, read its historical mathematical usage pattern, modern use, data requirements, and risks. A documented historic precedent is *not* a frequency count and never proves suitability on its own.
3. **Exclude charts with incompatible data semantics.** Do not force a geographic map without validated locations, Sankey without real source-to-destination links, radar without like-scaled multivariate profiles, stacked chart without verified additive components, or timeline without dated events. Reject comparative bars when each bar is measuring a different kind of MW, dollar, rate, or contract status.
4. **Compare the best THREE feasible chart styles** (or all when fewer) using the same dataset. Document: source-backed historical basis, modern fit, why discarded, and reader comprehension. Consider table/annotated schematic as a legitimate outcome rather than manufacturing a graph. Choose the format that communicates the true relationship; don't deliberately rotate into a worse chart merely for visual variety.
5. **Avoid the horizontal-bar reflex.** For *short category labels and ordinary comparisons*, prefer vertical columns when bars are truly the appropriate type; use horizontal bars for long names or crowded categories. Use line/step for observed time trends or discrete regime changes; scatter for measured numeric associations; waterfall for signed reconciled changes; dumbbell/slope for matched before/after; histogram/box/violin for distributions; treemap/stacked area for parts only when totals are verified; Sankey for auditable transfers; Gantt for dated project milestones. Not every numerical fact requires a bar chart.
6. **Rendering availability must never influence the analytical score.** When the ideal chart cannot yet be generated by SmartChart, use a sound external renderer or build a validated SVG (with source, units and axes); otherwise use a clearly sourced table or defer the visualization. Never silently replace it with a horizontal bar to satisfy a media quota.
7. **Verify the final chart** against source values, units, baselines, chronological order, sorting logic, percentages, status labels, alt text, responsive layout, caption, and correct footnotes. If a chart fails, fix → retest → replace/remake. Preserve the analytical audit and selected source citations in the article QA record.

## Publication evidence record

For each chart record: `datasetSource`, `sourceDate`, `claim`, `measurementUnit`, `dataStatus`, `chartSelected`, `historicalPattern`, `chartMethodSources`, `topThreeConsidered`, `rejectedAlternatives`, `orientationReason`, `dataValidation`, `renderingProof`, and `revisionNotes`.

## Research foundations

- [Financial Times Visual Vocabulary](https://github.com/Financial-Times/chart-doctor/tree/main/visual-vocabulary): chooses visual forms by the relationship central to a story.
- [Royal Statistical Society, Choosing a Visualisation Type](https://royal-statistical-society.github.io/datavisguide/docs/choosing.html): chart selection must account for data type, relationship, and audience.
- [From Data to Viz](https://www.data-to-viz.com/about.html): classify data input first; inspect all feasible options and their pitfalls.
- [Vega-Lite mark documentation](https://vega.github.io/vega-lite/docs/mark.html) and [encodings](https://vega.github.io/vega-lite/docs/encoding.html): quantitative/nominal/temporal channels and correct geometric encodings.
- [J-PAL / IPA's chart decision guide](https://data.poverty-action.org/data-science/data-visualization/communicating/choosing-the-right-chart.html): the analytical message should govern the chart, and a table is sometimes superior.

## Examples from the newsroom

- **Bitcoin mining efficiency 2025–2046 (J/TH):** observational time series → line chart with labeled historical dates, and a *separate* scenario line with forecast boundaries; no bar chart just because models have different values.
- **AIB old mining footprint 40 MW, future critical IT 50 MW, utility agreement 65 MW:** not comparable as one set of additive magnitudes. Prefer an annotated technical diagram or a status table (historic mine / contracted IT / utility agreement), not an unlabeled bar ranking.
- **Two proposed 25 MW halls expected by Q4 2027:** an annotated phase diagram/timeline might answer timing better than a two-bar chart that simply repeats the headline.
- **3 kW ASIC electricity costs in four countries:** four independent comparable monetary totals could support a *vertical* bar chart; dates/price evolution need a line chart instead.
- **Mining electricity draw versus delivered hashrate:** paired field measurements support scatter plots and regression intervals, not a bar comparison of unrelated units.
- **A planned energy-source mix:** use stacked area only if all components form a complete consistent total over time; do not stack statuses, contractual values and actual generation.

**Evidence limitation:** the catalog has two curated historical/method references per format, but those references support chart-type guidance rather than proving the numerical facts in any particular news article. Dataset provenance must be cited separately, without exception.
